# 生楽器ピッチ挙動トレース・プラグイン 構想メモ（v0.3）

作成日: 2026-09-20 / 最終更新: 2026-09-21
ステータス: 構想 + v0.4 プロトタイプ実装済み（`pitch-trace/` 参照。L0 エンジン・CLI・解析・IGF・参照演奏の転写・リアルタイム）
仮称: **PitchTrace**（以下、本メモではこの名で呼ぶ）

---

## 1. 一言でいうと

バイオリン・チェロ・オーボエ・サックスなど**単旋律の生楽器が「音程をどう揺らし、どう繋ぎ、どう外すか」**を録音から学習し、
その挙動を **(A) MIDI 打ち込みに自動付与**、**(B) 既存のオーディオ（Melodyne 等で扱う素材）に適用**できるツール。

打ち込みが「平板」に聴こえる最大の原因のひとつは、ピッチが完全に静止していること。
ベロシティやタイミングのヒューマナイズは既存ツールで足りるが、**ピッチの人間らしさ**を楽器ごとに再現するツールは実質存在しない。そこを狙う。

---

## 2. 何を「挙動」として捉えるか（ピッチの分解モデル）

ピッチを「平均律の目標音からのセント偏差 c(t)」として時間関数で扱い、次の成分の**和**として分解する。
この分解が本プロジェクトの核で、学習・生成・UI のすべてがこの単位で動く。

```
c(t) = イントネーション偏差(音)        … 音ごとの中心ピッチのズレ（定数）
     + 遷移(t)                          … 前の音からのポルタメント / レガートの繋ぎ
     + アタック(t)                      … 発音直後のしゃくり・オーバーシュート
     + ビブラート(t)                    … 周期的揺れ（遅れて始まり、育ち、減衰する）
     + ドリフト(t)                      … サステイン中のゆっくりした揺らぎ
     + リリース(t)                      … 音の終わりの落ち込み / 抜け
     + ノイズ(t)                        … 微細なジッタ
```

| 成分 | 主なパラメータ | 何に依存するか（条件） |
|---|---|---|
| イントネーション偏差 | セント値 | 音階上の役割（導音は高め、3度は純正寄り等）、楽器の構造（弦の開放弦、管の音域ごとの癖） |
| 遷移 | 開始遅れ、所要時間、カーブ形状（S字/指数）、非対称性、オーバーシュート | 音程差（跳躍幅・方向）、前音の長さ、テンポ、レガートかタンギングか |
| アタック | 開始オフセット（下から/上から）、収束時間 | 楽器種（サックスは下から、弦は指の到達で上下どちらも）、ダイナミクス、フレーズ先頭か |
| ビブラート | レート(Hz)、深さ(cent)、開始遅延、立ち上がり時間、波形の非対称、中心位置（目標音の下寄りか） | 音の長さ、ダイナミクス、音域、フレーズ位置（クライマックスで深く速く） |
| ドリフト | 低周波の振幅・時定数 | 音の長さ、息の残量（管）、弓の位置（弦） |
| リリース | 落ち込み量、時間 | 次の音との関係（フレーズ末か）、ダイナミクス |

**楽器ごとの傾向（目安・要実測）**

- バイオリン / チェロ: ビブラートは目標音の**下側**を中心に揺れることが多く、レート 5〜7 Hz、深さは数十セント。ポジション移動を伴う跳躍で明確なポルタメント。
- オーボエ: ビブラートは横隔膜由来でレート 5〜6 Hz、比較的浅い。アタックは安定しやすく、しゃくりは少ない。
- サックス: 下顎の緩めでピッチが下がるため、ビブラートは**下方向**中心。ジャズではアタックのスクープ（下からしゃくり上げ）と音末のフォールが顕著。クラシックとジャズで挙動が大きく異なる。

→ 「楽器」だけでなく「奏法スタイル（クラシック / ジャズ / ポップス）」を軸として持つ必要がある。

## 3. 学習パイプライン

```
録音（単旋律・無伴奏）
  → F0 抽出（CREPE / PESTO / pYIN、10ms 以下のホップ）
  → ノート分割（F0 + オンセット → 音符列。楽譜/MIDI があれば DTW でアライン）
  → 音符ごとに c(t) を切り出し、上記成分へ分解（パラメータ推定）
  → 条件（音程差・長さ・ダイナミクス・フレーズ位置 …）と対で保存
  → 楽器 × スタイル ごとの「プロファイル」を構築
```

### 3.1 データ

- **自前録音**を第一に考える（AtoZ の生徒・講師ネットワークを活かせる。ライセンスが明確で商用利用に問題がない）。
  楽器ごとに 30〜60 分、スケール・ロングトーン・跳躍練習・実曲フレーズを含む「収録メニュー」を設計する。
- 既存データセット（研究・検証用途。商用モデルに使う場合はライセンス確認が必須）:
  URMP（弦・管の単旋律ステム + 楽譜）、Bach10、MedleyDB のソロステム、Good-sounds、TinySOL / OrchideaSOL（単音のみで文脈がないため補助的）。
- **ユーザー自身の録音からプロファイルを作る**機能（few-shot）を製品の目玉候補にする。

### 3.2 モデル（段階的に）

| 段階 | 方式 | 狙い |
|---|---|---|
| L0 | ルール + 統計（各パラメータの条件付き分布からサンプリング） | 少データで動く。解釈でき、ノブで直接いじれる。まずこれで製品化まで持っていける |
| L1 | 条件付き生成モデル（音符列 → セント偏差カーブ）。小型 Transformer / CNN、または DiffSinger 系のピッチ予測器と同型 | フレーズ全体の文脈（山場でビブラートが深くなる等）を自然に扱う |
| L2 | スタイル埋め込み（奏者固有の癖）。ユーザー録音から埋め込みを推定 | 「あの人っぽさ」の再現 |

先行研究で最も近いのは **MIDI-DDSP**（Google Magenta, 2022）。音符 → 表現パラメータ（ビブラート・音量等）→ 合成、を URMP で学習している。
表現パラメータ層の設計はそのまま参考になる。ただし本プロジェクトは合成までやらず、**表現パラメータを既存の音源 / オーディオに渡す**ところに絞る。

## 4. 出力先（適用先）

### 4.1 MIDI 打ち込みへの適用

生成した c(t) を MIDI に落とす。対象楽器はすべて単旋律なので、ポリフォニーの問題はほぼ回避できる。

- **ピッチベンド**（1 ch）: 最も互換性が高い。ベンドレンジ（±2 / ±12 / ±48）を音源側と合わせる設定が必要。
- **MPE / MIDI 2.0 per-note pitch**: 音が重なる（レガートで前の音が残る）場合に必要。対応音源では第一候補。
- **CC 出力**: 音源がビブラートを CC1 等で制御する設計の場合、ビブラート成分だけをピッチベンドではなく CC に振り分ける「レーン分割」を持つ。
  同様にダイナミクス（CC11 / CC1）や微小タイミングも将来同じ枠組みで出せる。

**注意点: サンプル音源との相性**
Kontakt 系の多くはビブラートやレガート遷移が録音に焼き込まれており、外からピッチベンドを重ねると二重にかかる。
相性が良いのは物理モデル / モデリング系（SWAM、Sample Modeling、Infinite Series 等）や、ビブラートを CC で制御できる音源。
製品側では「音源プリセット」を持ち、どの成分をどのレーンに出すかを音源ごとに切り替える。

### 4.2 Melodyne / オーディオへの適用

**前提として、Melodyne には第三者がピッチカーブを書き込む公開 API がない**（ARA は DAW が Melodyne を組み込むための規格で、外部からデータを注入する用途ではない）。したがって選択肢は次の 3 つ。

1. **半自動ワークフロー**: PitchTrace が音符ごとの「レシピ」（中心ピッチ偏差、ビブラート深さ/レート、ドリフト量）を出し、ユーザーが Melodyne の Pitch Modulation / Pitch Drift マクロで適用する。実装コストは最小だが手作業が残る。
2. **自前 ARA プラグイン**: JUCE の ARA 対応を使い、DAW 上でオーディオを解析 → 音符分割 → c(t) を重畳したピッチシフトを自前で行う。ピッチシフタは Signalsmith Stretch（MIT）等の高品質ライブラリが使える。Melodyne に依存しない代わりに開発コストは大きい。
3. **MIDI 経由の再構築**: Melodyne からノートを MIDI 書き出し → PitchTrace で表情付け → 音源で再生。オーディオそのものは加工しないので用途が限られる。

推奨: **1 で価値検証 → 2 を本命**。「Melodyne 対応」は当面 1 の意味で謳う。

## 5. 製品形態とアーキテクチャ

```
[Research 層]  Python: F0 抽出・分解・学習・可視化（ノートブックで挙動を確認しながら進める）
      ↓ 学習済みモデル / プロファイル (ONNX + JSON)
[Core 層]      C++ or Rust: 分解モデルの生成器、MIDI/MPE レンダラ、（後期）ARA ピッチ処理
      ↓
[製品 A] スタンドアロン App   … MIDI/音声ファイルを読み込み → 表情付き MIDI を書き出し。最初に作る
[製品 B] MIDI FX プラグイン    … VST3 / AU / CLAP。DAW 内でリアルタイムに付与
[製品 C] ARA オーディオプラグイン … 4.2 の選択肢 2
```

**リアルタイム動作の考え方（製品 B）**
ポルタメントは「新しい音のノートオン時に、前の音のピッチから滑る」形で実装すれば未来の音を知らなくてよい。
アタック・ビブラート・ドリフトも同様に現在の音だけで決まる。フレーズ全体の文脈を使う L1 モデルはオフライン（製品 A）専用とし、リアルタイムでは L0 を使う二段構えにする。

**UI の骨子**

- 楽器 × スタイルのプリセット選択
- 成分ごとのノブ: Intonation / Portamento / Attack / Vibrato(Depth, Rate, Delay) / Drift / Release / Amount（全体量）/ Seed
- ピアノロール上に生成されたピッチカーブをオーバーレイ表示（何が起きているかを見せるのが教育的にも重要）
- 「Learn from audio」: ソロ録音をドロップしてプロファイルを作る

## 6. 既存ツールとの位置づけ

| 既存 | できること | PitchTrace との差 |
|---|---|---|
| DAW のヒューマナイズ | タイミング・ベロシティの乱数化 | ピッチは扱わない |
| 音源内蔵のレガート / ビブラートスクリプト | 音源ごとの固定挙動 | 楽器・奏者・文脈で変わる挙動を、音源をまたいで再現 |
| Melodyne の Pitch Modulation / Drift | 既存の揺れの増減 | 揺れの「生成」と楽器ごとの型を持つ |
| SWAM 等の物理モデル音源 | ベンド / MPE に自然に反応 | **相性の良い出力先**であり競合ではない |
| MIDI-DDSP（研究） | 音符 → 表現 → 合成 | 合成せず、既存の音源・オーディオへ表現だけを渡す |

## 8. リスクと未決事項

- **音源との二重がけ**: 焼き込み型サンプル音源では効果が出にくい。対応音源リストとプリセットで案内する。
- **Melodyne 直接連携は不可能**: 4.2 の通り。「Melodyne 対応」の表現に注意。
- **データのライセンス**: 研究用データセットは商用学習に使えない可能性が高い。自前録音を主軸にする。
- **ピッチ以外の表情**: 本当に自然に聴こえるにはダイナミクス（息・弓圧）と微小タイミングも要る。同じ分解の枠組みで拡張できる設計にしておくが、v1 はピッチに絞る。
- **単旋律の前提**: 対象楽器はすべて単旋律。ピアノ・ギター等の和音楽器は対象外とする。
- **未決**: 実装言語（C++/JUCE か Rust か）、モデル推論の載せ方（ONNX Runtime をプラグインに同梱するか）、製品 A を先にするか B を先にするか。

## 10.5 セットアップの確実性を機能として扱う（v0.4）

試用の失敗は、モデルの質ではなく環境と DAW 設定で起きる。特にベンドレンジの不一致は、
表情の量がそのまま音程の狂いとして出るため、聴感評価そのものを無意味にする。
ここを「手順書に書く」ではなく「コマンドで確かめられる」ところまで落とした。

| 判断 | 採否 | 理由 |
|---|---|---|
| 環境診断コマンド `doctor` | 採用 | 離れた場所から支援するとき、環境を再現せずに原因を絞り込める。`--json` の出力を貼るだけで済む |
| 診断の失敗判定を必須項目だけに限る | 採用 | MIDI ポートが無い環境（CI の Linux、DAW 未起動の Mac）でも `render` は使える。警告と失敗を分けないと「失敗」が無意味になる |
| 仮想ポートを実際に作って閉じる実地テスト | 採用 | rtmidi が入っていることと、CoreMIDI にポートを作れることは別問題。後者が `live` の成否を決める |
| ベンドレンジ検査 MIDI `bendcheck` | 採用 | RPN 0 を無視する音源が多く、規格上の通知だけでは担保できない。「同じ高さに聞こえるはずのペア」なら音楽の訓練が無くても判定できる |
| 検査を WAV で配る案 | 不採用 | 検査対象は DAW 側の音源設定なので、こちらで合成した音を聴いても意味がない |
| マーカーを日本語にする案 | 不採用 | MIDI のマーカーは latin-1 しか格納できない。英数字にして、読み方は CLI と文書で日本語で示す |
| ベンドレンジ既定値を下げる案 | 不採用 | 14 ビット固定なので ±12 半音でも 0.15 セント刻み。可聴差（約 5 セント）に対して十分細かく、オクターブ跳躍のポルタメントを残せる利点が上回る |
| `setup_mac.sh --logic` で確認ファイル一式を生成 | 採用 | 「何を読み込んで何を聴くか」まで決めておかないと、最初の 15 分で詰まる |

## 11. 自己改善の運用

- `pitchtrace eval --all` で往復精度を数値化し、`pitch-trace/docs/EVAL_LOG.md` に版ごとに記録する
